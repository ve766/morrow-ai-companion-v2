### 3 处命中的判定

三处命中是同一个字符串，长度 22，出现在三份文档的"风险与依赖"表格中。读上下文后确认它不是令牌，而是文件名 `docs/audit/morrow-v2-risk-dependency-register.md` 里 `ri**sk-d**ependency-register` 这一段被正则当成了令牌。掩码一致（同前缀同长度），三处指向同一文件名，无第四处。

判定为误报的依据是上下文，不是猜测：命中位置的左右两侧都是文件名字符，且该文件确实存在于 `docs/audit/`。

## 由此暴露的缺陷（已修）

抹除函数 `assertNoSecret` 用的是同一条无边界正则，这意味着**任何引用该文件名的评估产物都会在写出前抛出"凭据泄漏"并中止**。误报在这个函数里尤其危险：看到报错的人下一步往往是放宽正则，而放宽之后真泄漏就再也拦不住了。

修复：给正则加左边界 `(?<![A-Za-z0-9_-])`，使其只匹配独立令牌位置（前面是引号、等号、空格、冒号或行首），不匹配标识符内部的子串。

## 补充发现：一条会诱导违规的遗留便条（2026-11-01 复核）

`.tmp/WHERE_TO_PUT_KEY.txt`（87 字符）写着"把 key 粘到下面这个文件里……`.tmp/deepseek.key`"。

- 该文件**不含任何凭据**：key 形状扫描与 `MORROW_TEST_API_KEY` 变量名扫描均为 `false`。
- 它指向的 `.tmp/deepseek.key` **并不存在**。
- 危险的不是内容，是指令：它教人把凭据落盘，而运行器**没有文件回退**（单一入口 `MORROW_TEST_API_KEY`）。照做的人会得到"粘了 key 却仍是 BLOCKED"的困惑，下一个动作往往是去改探针读文件——那正好把一条安全设计拆掉。

建议删除该便条。若确实需要密钥文件方案，应由运行器显式支持并写进契约，而不是靠一张便利贴。
