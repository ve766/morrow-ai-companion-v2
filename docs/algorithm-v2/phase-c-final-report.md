## 2. C1：子串匹配缺陷

### 缺陷

```ts
normalized.includes(term)     // "an" 命中 "analyst"
normalized.includes(phrase)   // "tea" 命中 "steam"
```

实测后果（均为真实案例）：

| 查询 | 记忆 | 旧行为 |
|---|---|---|
| What is the airspeed of an unladen swallow? | I work as a data analyst. | `an` 命中 `analyst` → **召回** |
| What pet do I have? | I have a dog named Pixel. | `do` 命中 `dog` → **召回** |
| Do I like scary movies? | I dislike horror films. | `like` 命中 `dislike` → **召回** |

### 修复策略（按书写系统）

| 文本 | 匹配单位 | 例子 |
|---|---|---|
| 拉丁 / 数字 / 混合 token | 完整 token | `26` 不再命中 `2026` |
| 中文 | 相邻二字组（bigram） | `喜欢素食` ↔ `我更喜欢素食` 命中；`食主` 不命中 |
| 中英混合 | 分 run，各用各的规则 | `咖啡 coffee` 命中短语；`咖啡 tea` 只命中中文词项 |

归一化仍是 `NFKC` + 小写。`substring` 保留为显式配置（`lexicalMatching`），仅用于复现冻结基准，非默认。

### 24 个回归测试

每个「不命中」用例**同时断言旧模式命中**，证明测试能区分两种行为。验证方式：临时把默认改回 `substring`，端到端用例失败（v2/v3/默认值断言），恢复后通过。

### 新旧检索结果

**Phase A 冻结基准（12 例）：聚合指标零变化。** 逐案例只有 `multi-topic-week-planning` 的第 4–6 位顺序变化。这解释了为什么 Phase A 没发现缺陷 —— 该基准的查询都用足够长的内容词。

| 指标 | v1 (2.1.0) | v1 (2.2.0) | v2 (2.1.0) | v2 (2.2.0) |
|---|---|---|---|---|
| Recall@1 / MRR | 0.6528 / 0.9167 | 同 | 0.7361 / 0.9583 | 同 |
| 泄漏 / 顺序违规 / 重复对 | 1 / 1 / 6 | 同 | 0 / 0 / 0 | 同 |

**语义三段集：精度上升，词法召回下降（原因是正确的）。**

| 臂 | dev r1 | dev 错误率 | val r1 | val 错误率 | holdout r1 | holdout 错误率 |
|---|---|---|---|---|---|---|
| v2 词法 | 0.5769→**0.5000** | 0.1410→**0.0385** | 0.7917→**0.6250** | 0.2500→**0.0833** | 0.4583→**0.5417** | 0.1250→**0.0833** |
| v3 混合 | 0.9615→0.9615 | 0.1410→**0.0641** | 0.9583→0.9583 | 0.2083→**0.0833** | 0.7917→0.7917 | 0.0833→0.0833 |

词法召回下降的三个案例逐一核对，全部是**偶然子串命中被移除**；混合臂的召回、MRR、NDCG 在三段上**完全不变**，说明 Phase B 的语义结论不依赖这些假阳性。

**版本关系**：`RetrievalConfig 2.1.0`（substring，旧数字）→ `2.2.0`（token，新数字）；旧结果保留在 `retrieval-benchmark-v1-frozen-config-2.1.0.json`，未被改写。

## 3. C2：失败根因

诊断工具：`node scripts/diagnose-retrieval-case.mjs --case <id>`，逐记忆输出词法分、余弦、归一化语义分、融合前后排名、排除原因与最终交给模型的上下文。

### 失败一：「买表 ↔ 攒首付」= 能力边界

```
cosine("Should I buy this expensive watch?", "I am saving for a house deposit.") = 0.056
候选门限 0.28 → 不进入候选集
最终上下文: {"memories":[]}
```

关联是**经济约束推理**，不是分布相似性。0.056 低于不相关样本的**中位数**（0.331）。把门限降到 0.05 会让空证据场景失效。**这是能力边界，不是阈值 bug。**

### 失败二：「我有什么爱好」↔ `I collect vinyl records` = 门限边界

```
cosine = 0.246，门限 0.28；排序是对的（0.246 vs 0.050）
```

只差 0.034。**但没有调门限** —— 该值来自留出集，用它调参违反纪律。dev/validation 里没有任何期望记忆落在 0.20–0.28 区间，因此**没有证据**支持下调。正确路径是下一阶段构造含 0.20–0.28 区间正例的新开发集。

### 对照证据（最有力的一条）

```
hold-semantic-contradiction-coffee:
  coffee-restated  cosine 0.660   ← 比正确答案更高，且是禁止项
  coffee-quit      cosine 0.643   ← 正确答案
  结果: 禁止项被 superseded_statement 排除，正确项被召回
```

**语义模型在这里是错的，系统没有跟着错** —— 因为纠正链判定在任何打分之前。这直接证明「语义相似度不是事实置信度」不只是口号。

真实请求体验证：`retrieval-failure-diagnosis.integration.test.ts` 3 例（真实模型），断言两个失败案例的 system 确实是 `"memories":[]`，对照案例确实包含纠正后的记忆。

## 4. C3：新基准

三段 v2 数据集（v1 原样保留）：

| 数据集 | 版本 | 案例数 | fixture sha256（前 12） |
|---|---|---|---|
| dev v2 | 2.0.0 | 16 | `37528ca1ea52` |
| validation v2 | 2.0.0 | 15 | `9fd71357a65c` |
| holdout v2 | 2.0.0 | 15 | `62525d93456b` |

新增场景：**多次修订纠正（A→B→C）**、**同主题大量重复**、**上下文预算限制**。

### 留出 v2 结果

| 臂 | Recall@1 | MRR | NDCG@5 | 错误相关率 | 泄漏 |
|---|---|---|---|---|---|
| v2 词法 | 0.6000 | 0.6667 | 0.6409 | 0.0667 | 0 |
| **v3 加权** | **0.8000** | **0.8667** | **0.8667** | 0.0667 | **0** |

**不确定性（必须报告的部分）**：v3 首位命中 11/12 = 1.0000，Wilson 95% 区间 **[0.7412, 1.0000]**；无泄漏 15/15，区间 **[0.7961, 1.0000]**。**即使测得满分也不能说召回率 100%**；泄漏安全性依据的是实现（过滤顺序 + 纠正链），不是统计。

### 新场景全部通过

- **多次修订**：两次纠正后，两个旧驻地都被 `superseded_statement` 排除，泄漏 0
- **重复簇**：v3 去重后返回 4 条且顺序多样化，未召回无关记忆
- **预算**：8 条 / 2796 字符（上限 3000），最新的两条排最前

### 加权 vs RRF：这次分出了胜负

Phase B 报告说「两者 37 例排序完全相同，选加权只是因为可审计」。加入新场景后**加权在三个 v2 集合上都优于 RRF**（0.9375/0.9333/0.8000 vs 0.9063/0.9000/0.7667）。Phase B 的那条结论**已过时**，本报告更正。

### 一处门禁失败，如实保留

开发 v2 上 `hybridFalseRelevantNotWorse` 失败：v3 错误相关率 0.0521 > v2 的 0.0313。差异来自一个案例（`espresso`，咖啡机购买记录）被语义准入。**未为此调门限**，失败保留在报告里。

## 5. C4：部署决策

| 项 | 实测 |
|---|---|
| 模型 | 112.8 MB q8 ONNX，目录 130 MB，**Apache-2.0**（HF API 确认） |
| 冷加载 | 1514 ms 墙钟 / 2671 ms CPU（进程冷、文件热） |
| 同进程二次加载 | 1502 ms（**不缓存**，所以编码器做了缓存） |
| RSS | 空闲 65 MB → 加载后 476 MB → 查询中 497 MB（**+411 MB**） |
| 单条查询 | 6.2 ms 墙钟 / 36.0 ms CPU（ORT 多线程） |
| 失败模式 | 模型缺失、文件损坏 → 抛错 → 分类 → **词法回退**；惰性加载器记住失败，不逐回合重试 |
| **安装包（现状）** | **106.49 MB**（实测） |
| **安装包（随包分发）** | **174.96 MB**（实测，+68.5 MB / 1.64×；解包 +129 MB） |

安装包测量方式：真实运行两次 `npm run package:win`，第二次临时加入运行时与模型；测量后配置已还原（`git diff package.json` 为空）。

**建议：方案 B（用户明确同意后一次性下载），作为目标设计。** 但**本阶段未实现下载流程**，当前状态是「手动放置模型文件」。方案 B 仍需运行时进安装包（估算约 140 MB，未单独实测）。

阻止最终决策的信息：开启语义检索的用户比例、分发带宽约束、是否必须支持完全离线安装。
