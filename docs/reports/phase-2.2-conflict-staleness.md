# Phase 2.2 — 冲突、过期、纠正与不确定性（任务 2 / 任务 3）

- 相关提交：`2b536aa`
- 证据层级：系统层（源码 + 自动测试）与模型层（真实本地模型）分开陈述

## 1. 冲突：从「两条都发」到「可追踪的冲突组」

### 1.1 基线

Phase 2.1 的结论是：两条冲突记录都会进入请求，但 `detectConflicts` 只写事件，不把「它们互相冲突」这件事交给模型；模型在 4/4 次运行里都只选了一条。也就是说，系统做到了「都送到」，没做到「让模型知道需要处理冲突」。

### 1.2 修改

在装配阶段，对**已选中的**记录做结构化分组：

- 两条记录共享 ≥ 2 个显著词项（拉丁整词 / 中文 bigram），且规范化文本不同 → 同一个 `conflictGroup`。
- 分组结果写进请求里的每条记录：`"conflictGroup": 0`。
- 指令明确写：`conflictGroup may contradict: ask which is current`。

### 1.3 为什么只叫「可能冲突」

`我住在杭州` 与 `我搬到上海了` 共享词项不足，不会被分组；`我住在杭州` 与 `我住在上海` 会被分组，但它们也可能只是**时间变化**，不是矛盾。系统无法在不理解语义的情况下区分：

- 用户明确纠正（已有 `correct` 状态机与 revision，见 §3）；
- 两条确实矛盾；
- 随时间变化；
- 无法判断。

因此分组只声明「可能矛盾」，并要求模型**说出来并询问**，而不是宣称某条为假。

### 1.4 证据

| 检查 | 结果 |
|---|---|
| 同主题两条 → 同一组 | 单测通过（`conflictGroup = [0,0]`） |
| 不同主题不分组 | 单测通过（`undefined`） |
| 请求体含冲突指令 | `context-memory-v2` 的 `v2-conflict-group` 通过 |
| 真实模型是否披露 | **未通过**：runId `20261027T062902Z-e0151c`，回复「你住在中国，我住在美国」，两个城市都没提，判定 `fail`，归因 `delivered_but_not_used` |

## 2. 过期：从统一 180 天到按波动性分档

### 2.1 基线

`isStaleMemory` 对所有记忆使用同一个 `MEMORY_STALE_DAYS = 180`。这会把「喜欢的食物」过早标旧，也会把「正在找工作」标得太晚。

### 2.2 修改

新增确定性的波动性分类（`memory-domain.ts`）：

| 类别 | 标记（示例） | 窗口 |
|---|---|---|
| `volatile` | 住在 / 工作 / 工资 / 年龄 / 怀孕 / 离婚 / 计划 / 最近 / live / job / salary / currently | 90 天 |
| `stable` | 喜欢 / 偏好 / 习惯 / 过敏 / 信仰 / 性格 / like / prefer / always / allergy | 365 天 |
| `unknown` | 无标记 | 180 天（保持原行为） |

请求体新增两个可审计字段：`volatility`（`unknown` 时省略）与 `ageDays`。这样「为什么标 stale」不再只是一个布尔值。

### 2.3 不伪造

- 不修改 `confidence`、`lastConfirmedAt`、`updatedAt` 来「制造」新鲜度。
- 过期不等于删除：记录仍可召回，只是带 `stale: true` 与「未经确认」的指令。
- 用户 `confirm` 仍走原有状态机（revision +1，confidence +5，上限 100）。

### 2.4 证据

| 检查 | 结果 |
|---|---|
| 120 天：volatile 过期、stable 不过期、unknown 过期 | 单测通过 |
| 400 天：stable 也过期 | 单测通过 |
| 请求体携带 `volatility` / `ageDays` | `v2-stale-classes` 通过（`volatility` 出现，`ageDays = 120`） |
| 模型是否承认不确定 | **未验证**：`v2-stale-classes` 无机械规则，真实运行判定 `needs_review` |

### 2.5 为什么过期不设自动判定

Phase 2.1 已证明：任何子串规则都会被「照读记忆」满足（回复里出现「南京」就算通过），反而奖励错误答案。本阶段维持 `needs_review`，把判断交给人工复核，而不是降低标准。

## 3. 纠正与撤回

本阶段没有改纠正链，只验证它在新检索层下仍然成立：

| 场景 | 结果 | 证据 |
|---|---|---|
| 纠正后旧值不再出现 | 通过 | `v2-correction-current`：请求含「杭州」、不含「上海」 |
| 撤回后不进入请求 | 通过 | `v2-retracted-context`：`memoryEntries = 0`，哨兵不出现 |
| 删除后各路由都不出现 | 通过 | 既有 `drops a deleted memory on every route` |
| 纠正后 revision 可追溯 | 通过 | 既有 `preserves original text and a complete linear correction lineage` |

**注意**：`v2-correction-current` 的系统层通过，不代表模型会用。真实运行里模型答「我住在北京」，判定 `fail`（`delivered_but_not_used`）。

## 4. 模型层结论（如实）

| 能力 | 系统层 | 模型层 |
|---|---|---|
| 冲突双方都送达 | 已证实 | 0/1 通过（1 次 fail） |
| 纠正后新值送达、旧值不送达 | 已证实 | 0/1 通过（模型编造第三座城市） |
| 过期标记送达 | 已证实 | 未验证（`needs_review`） |
| 模型主动说明冲突 | 指令已送达 | 未观察到 |

`qwen2.5:0.5b` 的能力不足以支撑「冲突披露」与「过期承认」的行为层结论。本阶段不据此宣称 Morrow 已具备这两种能力。

## 5. 残余风险

1. 冲突分组是词面启发式：同义改写（「住处」vs「住在」）可能漏分组；共享词多但主题不同的两条可能误分组。
2. 波动性分类是标记表，不是理解：未覆盖的表达会落到 `unknown`（180 天），不会静默变成 `stable`。
3. 冲突没有「哪条更新」的时间裁决；系统只把双方与指令送到模型，不代替用户决定。
4. 模型层的两种失败都是真实记录，未通过调低判定标准来「修复」。
