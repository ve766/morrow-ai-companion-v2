## 6. 数据库升级与恢复验收

### 6.1 升级保留数据

对 v11 / v17 / v18 / v20 四个起点，各自写入同一组合成数据（会话、消息、记忆 + 修订、人格版本、Provider 配置、反馈候选 + 证据、删除日志），再用 `SqliteDatabase.open` 升级到 v21。

|---|---|---|---|---|
| v11 | 21 | 一致 | 标题/正文/记忆正文/人格版本/Provider 行 | ok / 空 |

v11 起点没有 `sensitivity` / `confidence` / `local-openai` 行，测试按实际列集与允许的 provider 行构造数据——这正是「旧库长什么样就按什么样升级」，不是把新库塞回旧版本。

### 6.2 升级中的人为失败

| 场景 | 做法 | 结果 |
|---|---|---|
| 迁移函数抛错 | 用真实迁移 1–20 + 一个故意失败的 v21 | 版本停在 20、行数不变、`integrity_check=ok`、记忆正文仍在；随后正常打开可继续升级到 21 |
| 半应用状态（列已存在） | 手工 `ALTER TABLE provider_profiles ADD COLUMN active`，让 v21 撞重复列 | `SqliteDatabase.open` **降级打开到 v20**（不是崩溃），并保留 `.bak` 快照 |

第二种是关键：失败的可选迁移不能把整个数据库弄死。降级打开是有意的产品行为，快照保留是恢复手段。

### 6.3 恢复快照

`morrow.sqlite3.pre-v20-to-v21-<ts>-<uuid>.bak`：

### 6.5 凭据不在库里、也不在备份里

| 断言 | 结果 |
|---|---|
| `provider_profiles` 没有 `api_key` / `credential` 列 | 通过 |
| 备份目录只有 `manifest.json` + `morrow.sqlite3` | 通过 |
| 两个文件都不含哨兵字符串 | 通过 |
| manifest 只有 `application / counts / createdAt / database / format / formatVersion` | 通过 |

凭据的实际存储是 Electron `safeStorage`（OS 凭据后端）加密后单独落盘的 `.bin` 文件，**不在 SQLite 里，因此 `VACUUM INTO` 快照天然不含它**。这意味着：备份不携带凭据，恢复后需要重新配置 key——这是有意的安全取舍，写在报告里而不是当作缺陷。

### 6.6 新 schema 在旧代码下的行为

往 v21 库里插一条 v22 的 `schema_migrations` 记录模拟「新版本写过这个文件」，当前代码 `SqliteDatabase.open` 直接拒绝，且**不改动文件**：版本仍是 22、`integrity_check` 仍 ok。

用户可见后果是「需要恢复备份」——这正是 6.3 快照存在的理由。

## 9. 结论

- **当前代码实现了什么**：可配置的第三方 OpenAI 兼容 Provider（独立 provider id、https 强制、URL 归一化、按 provider 超时、目录探测、显式切换且失败不回退、凭据走 OS 加密存储）；分节记忆上下文与 7 维结构化判定；删除日志覆盖消息/证据/候选并能在恢复时重放；v21 显式 Provider 选择。
- **只在工程层通过的**：Provider 接入、配置校验、凭据不回显、显式切换、目录探测、错误分类；数据库升级与恢复的全部 10 条验收；592 条用例、5 个离线评估、构建。
- **已重复验证的真实模型行为**：本地 `qwen2.5:0.5b` 的 12 场景 × 5 次（跨会话召回 5/5、冲突披露 0/5、同会话召回 1/5、安全场景 0 违规）。
- **因额度/环境阻断的**：第三方模型行为评测（无凭据，未发请求）。上一轮的 403 额度不足是唯一原因。
- **数据升级、恢复、回滚是否有可重复证据**：升级与恢复**有**（10 条可重复验收）；回滚**只有说明没有自动化验证**——回滚意味着跑旧代码，仓库里没有旧构建，属于 `NEEDS_REVIEW`。
- **PR 能否保持开放**：可以。阻止合并的问题没有变化：冲突披露与同会话召回不达标、第三方行为评测缺失、无人工复核。
